# CLAUDE.md — Working in ExpresScan

This file is read by Claude Code at session start. It documents project-specific
conventions and workflow rules that override default behavior.

## Push policy: pushes to `main` ship to TestFlight

**Every push to `main` is a major piece of work and triggers a TestFlight
release.** Treat pushes as deliberate release events, not casual checkpoints.

The flow is mechanized by `.github/workflows/main.yml`:

1. Push to `main` → CI runs build, tests, lint, and format check.
2. If `check` passes, the `release` job:
   - Bumps `CURRENT_PROJECT_VERSION` / `CFBundleVersion` in `project.yml`
   - Archives & uploads via `bin/release-testflight.sh`
   - Polls App Store Connect until the build is `VALID`
   - Sets the TestFlight "What to Test" notes from commits since the last bump
   - Commits the build bump back to `main` with `[skip ci]`

What this means for how I work:

- **Group related commits onto a feature branch and open a PR** rather than
  pushing tiny incremental commits straight to `main`. The PR runs `check`
  for fast feedback without releasing.
- **Push to `main` only when the change is genuinely ready to ship to
  TestFlight users.** Small refactors, tweaks, or work-in-progress don't
  belong on `main` — they belong on a branch.
- **Never bypass the CI release** with manual `git push --force` or by
  skipping hooks. If a release fails, fix the underlying issue and let the
  workflow re-run.
- **Do not commit and push on behalf of the user without explicit
  authorization for the specific push** — even when working in a branch.
  The default policy across this repo is to confirm before any operation
  that publishes work outward (push, PR, release).

When the user asks for "ship this" or "release this" without further
qualification, default to: open a PR rather than pushing to `main` directly,
unless the user has named `main` as the target.

## Local TestFlight releases

`bin/release-testflight.sh` is the same script CI runs. Local invocations
use the `DEVELOPER_DIR_OVERRIDE` default (Xcode-beta); CI overrides it via
the env var. Don't hardcode the path further.

### Release config split

Real Apple Developer + App Store Connect identifiers live in
`bin/.release-config` (gitignored). Copy `bin/release-config.example` and
fill in:

- `APPLE_TEAM_ID` — from developer.apple.com (Account → Membership)
- `ASC_API_KEY_ID` — App Store Connect → Users & Access → Integrations → API Keys
- `ASC_API_ISSUER_ID` — same page
- `ASC_APP_ID` — App Store Connect → App → App Information → Apple ID
- `RELEASE_DEVICE_ID` (optional) — UDID of the test iPhone for `--skip-device=false`

The ASC API key `.p8` file lives at
`~/.secrets/expresscharge/AuthKey_${ASC_API_KEY_ID}.p8`.

CI does NOT use `.release-config`; it gets the same values from repo Variables
(`vars.APPLE_TEAM_ID`, `vars.ASC_API_KEY_ID`, etc.) injected as env vars on
the release job.

## Local CI fallback

When GitHub Actions is unavailable, `bin/precommit.sh` reproduces most of CI
locally. Per workflow job:

| CI job        | Local equivalent                                              |
|---------------|---------------------------------------------------------------|
| `lint`        | `xcrun swift-format lint --recursive --strict App Sources Tests ExpresScanTests ExpresScanUITests` |
| `format`      | `xcrun swift-format format --recursive -i …` then `git diff --exit-code` |
| `build`       | `xcodegen generate && xcodebuild -scheme ExpresScan-Release build-for-testing -destination 'platform=iOS Simulator,name=iPhone 17 Pro,OS=latest'` |
| `test-unit`   | `xcodebuild test -scheme ExpresScan-Debug -only-testing:ExpresScanTests` |
| `test-ui`     | `xcodebuild test -scheme ExpresScan-Debug -only-testing:ExpresScanUITests` |
| `release`     | `bin/release-testflight.sh` (requires bin/.release-config + ASC key) |
| `secrets-scan`| `gitleaks detect --no-banner`                                 |

The `release` job is the only one that requires the ASC API key on the local
machine. All others run fully offline against the simulator.

## Build & test

- Project file is generated by `xcodegen` from `project.yml`. Never hand-edit
  `ExpresScan.xcodeproj/`. Run `xcodegen generate` after changing `project.yml`
  or after adding/removing files (xcodegen globs `App/`, `Sources/`, `Tests/`).
- App target uses `App/`; SwiftPM modules live under `Sources/`. The Xcode
  schemes are `ExpresScan-Debug` and `ExpresScan-Release` (the bare
  `ExpresScan` scheme name does not exist).
- Default destination for tests:
  `platform=iOS Simulator,name=iPhone 17 Pro,OS=latest`.

## Lint & format

- `xcrun swift-format` (Apple's swift-format, bundled with Xcode 16+) is
  the source of truth. Config lives at `.swift-format` and matches the
  codebase's existing 4-space indent + 100-column line length.
- CI runs lint and format check as **informational** today
  (`continue-on-error: true`) — they emit annotations but don't block the
  release. The codebase has accumulated drift the user will tighten up
  later. Do not auto-reformat unrelated files when making changes; only
  format files you're already touching.

## Style notes for this codebase

- Visual constants (color RGB tuples, geometry tables, status hue maps) are
  often deliberately column-aligned. Preserve that alignment when editing.
- The `App/Design/Components/` directory holds reusable visual primitives
  (icons, glyphs, status pills); `App/Features/<feature>/` holds
  feature-specific views and view-models.
- iOS 26 is the deployment target; full Xcode-beta is at
  `/Applications/Xcode-beta.app`. Most local tooling assumes that path.
